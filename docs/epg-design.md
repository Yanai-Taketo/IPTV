# EPG(電子番組表)機能の調査・設計

**日付**: 2026-08-04 / **ブランチ**: `claude/epg-api-implementation-wr635a`

「EPG などの API で実装できそうなものを調査・設計・製作・テストする」という要望に対する
調査結果と、この結果に基づいてこのブランチに実装した EPG パイプライン + 表示機能をまとめる。

## 1. 調査: iptv-org エコシステムに「番組表 API」は存在するか

結論: **番組データそのものをホストする API は存在しない**。ただし部品はすべて揃っている。

| リソース | 内容 | 使えるか |
|---|---|---|
| [iptv-org/api](https://github.com/iptv-org/api) `guides.json` | チャンネル/フィード → EPG 提供サイト(site, site_id, lang)のマッピング。約 18 万行・25MB | ✅ グラブ対象の選定に使用 |
| [iptv-org/epg](https://github.com/iptv-org/epg) | 200 以上のサイトから番組表を取得する公式グラバー(`npm run grab`)。**番組データは配布していない**(著作権上の配慮でユーザーが各自実行する設計) | ✅ CI で自前実行 |
| iptv-org 公式サイト | EPG 表示なし(グラバーの案内のみ) | — |

### 定量調査(2026-08-04 時点の実データ)

- `guides.json` 全 180,701 行のうち、チャンネルに紐づく行は 31,304 行(**11,717 チャンネル**)
- このリポジトリの再生可能性インデックス(`data/playability.json`)で
  「再生確認済み(status=1)」のチャンネルは 3,401 件
- **再生確認済み × ガイドあり = 1,462 チャンネル** — これが実用的なグラブ対象
- カバレッジ上位サイトはアグリゲータ系(i.mjh.nz、pluto.tv、plex.tv 等)で、
  少数サイトで大半のチャンネルを賄える(上位 40 サイトで 1,408/1,462 をカバー)

### グラバーの実行検証(この環境で実測)

- `npm run grab --- --channels=... --json --days=2 --maxConnections=5`:
  6 チャンネル × 2 日 = 12 リクエストを **21 秒**で完了
- 40 サイト × 80 チャンネル × 2 日のストラタファイドサンプルでも動作確認(§4)
- `--json` 出力は `{date, channels[], programs[]}` 形式で、番組は epoch ミリ秒の
  `start`/`stop`、`titles[]`、`descriptions[]`、`categories[]`、`episodeNumbers[]` などを持つ

## 2. 設計判断

### 2.1 なぜ「CI グラブ → 静的 JSON」方式か

| 案 | 判定 | 理由 |
|---|---|---|
| **A. CI で iptv-org/epg を実行し静的 JSON を生成**(採用) | ✅ | 既存の再生可能性プローブと同型のパターン(データ生成 → `data/` にコミット → Pages デプロイ)。ブラウザからは同一オリジン fetch で CORS 問題なし |
| B. ブラウザから外部 EPG サイトを直接取得 | ❌ | CORS 不可・スクレイピングをクライアントに埋め込むことになり脆い |
| C. `guides.json` へのリンク表示のみ | ❌ | 「番組表」の実体がなく体験価値が低い |
| D. 全 11,717 チャンネルをグラブ | ❌ | CI で数時間級・データ数十 MB 級。再生できないチャンネルの番組表は価値が薄い |

### 2.2 グラブ対象の選定(scripts/epg-lib.mjs `selectGuideRows`)

1. **候補** = 再生確認済み(playability status=1 のストリームを持つ)チャンネル
   (インデックスが無い環境ではストリームを持つ全チャンネルにフォールバック)
2. チャンネルごとにガイド行を 1 つ選ぶ:
   **メインフィード優先 → カバレッジの大きいサイト優先 → 辞書順**(決定性の担保)
3. **サイト数上限**(既定 40)で選定チャンネル数の少ないサイトから落とし、そこしか無い
   チャンネルは残りサイトで再選定、不可能なら除外(CI 時間の上限を守るため)
4. **チャンネル数上限**(既定 1,500)で決定的に切り詰め

### 2.3 配信データフォーマット(2 層構成)

一覧の「現在番組」表示は全チャンネル分を一括で読む必要があり、
説明文まで含めると数十 MB になるため 2 層に分ける:

```
data/epg/schedule.json      … 一覧用。全対象チャンネルの [開始秒, 長さ秒, タイトル]
                              (起動時に 1 回 fetch。GitHub Pages は gzip 配信するため実転送は約 1/4)
data/epg/details-<n>.json   … 説明文・サブタイトル・カテゴリ・話数入りの詳細シャード
                              (プレイヤーを開いたときに該当シャードだけ遅延 fetch)
data/epg/channels.xml       … グラバーに渡した選定結果(透明性・デバッグ用)
```

- 時刻は **UTC epoch 秒**(表示は閲覧者のローカル時刻に変換)
- シャード番号は `schedule.json` のチャンネルごとに記録 — フロントエンドは
  ハッシュ実装を持たず、生成側(FNV-1a)と食い違うリスクを排除
- `schedule.json` が 404 の環境(EPG 未生成)では **EPG UI が一切出ない**
  (再生可能性インデックスと同じグレースフルデグラデーション)

### 2.4 更新パイプライン(.github/workflows/grab-epg.yml)

```
毎日 05:07 UTC(再生可能性プローブの後)
  1. prepare  … API + playability.json から channels.xml(全体 + サイト別)を生成
  2. iptv-org/epg を shallow clone + npm ci
  3. サイトごとに別プロセスで npm run grab --- --json --days=2 --maxConnections=10
     (サイト単位で 15 分タイムアウト。失敗したサイトはスキップして続行)
  4. convert  … 全サイトの結果をマージして schedule.json + details-*.json へ変換
     (番組 0 件なら失敗させ、既存データを空で上書きしない)
  5. data/epg/ を履歴を持たない epg-data ブランチへ force-push → Pages デプロイ
```

**サイト単位の分割実行にした理由(実環境で確認した障害)**: 全 40 サイト・約 2,800
グラブを単一プロセスで実行したところ、全チャンネル分の XMLTV を一括返却するサイト
(epg.iptvx.one 等)の応答が同時に重なった時点で Node のヒープ(既定 4GB)が枯渇し
OOM でクラッシュした。iptv-org 本家がサイト単位のジョブ分割で運用しているのと同じ
構成に合わせ、メモリをサイト 1 つ分に抑えつつ、サイト側の障害・タイムアウトの影響を
そのサイトだけに隔離している(1 サイトでも成功すれば配信データは更新される)。

**main にはコミットしない。** 日次 15MB 級のデータを main に積むと履歴が年 1GB 超
肥大するため、`epg-data` ブランチを毎回作り直して force-push する(常に 1 コミット)。
各ワークフロー(deploy-pages / probe-playability / grab-epg)はデプロイ直前に
このブランチから `data/epg` を取り出してサイトに同梱するので、どの経路のデプロイでも
番組表は消えない。`data/epg/` は .gitignore 済み。

## 3. フロントエンド

- **チャンネルカード**: 現在番組(`▶ タイトル + 時間帯 + 進捗バー`)。現在番組が無い場合は
  次番組(`次 HH:MM タイトル`)。30 秒ごとに描画済みカードを更新して番組境界に追従
- **プレイヤーモーダル**: 現在番組 + 進捗バー + 説明文(詳細シャードから遅延取得)+
  「この後の番組」最大 5 件。30 秒ごとに更新
- **フィルタ**: 「番組表ありのみ (n)」チェックボックス(EPG データがある環境のみ表示)
- **グリッドヘッダ**: 番組表の取得時刻を「再生確認」と並べて表示

## 4. 実測値(このブランチでの E2E 検証)

| 項目 | 値 |
|---|---|
| 選定結果(既定設定) | 1,408 チャンネル / 40 サイト(候補 3,401、ガイドあり 1,462、サイト上限除外 54) |
| サンプルグラブ(全 40 サイトから各 2ch = 80ch × 2 日) | 2 分 08 秒、52ch / 28 サイトから 2,917 番組を取得(サイト側の失敗・データ欠落により取得数は選定数を下回る) |
| 変換後サイズ(52ch 分) | schedule.json 140KB(gzip 34KB)+ details 24 シャード計 576KB。終了済み番組 153 件をプルーニング |
| フルスケール推定(約 1,400ch) | schedule 約 4MB(gzip 約 900KB)+ details 計 15MB 前後。main にコミットすると履歴が約 3MB/日(年 1GB 超)肥大するため、履歴を持たない epg-data ブランチへの force-push 方式を採用(§2.4) |
| ブラウザ統合確認 | 実 API スナップショット + 実グラブデータで、一覧の現在番組表示 52/52・フィルタ・プレイヤーパネル(現在+この後 5 件+説明文)・ページエラー 0 を確認 |

> 数値はデータソース側の日次更新で変動する。データ量を抑えたい場合は
> workflow_dispatch の取得日数を 1 日にする・`--max-channels` を下げる・cron を隔日にする、で調整できる。

## 6. 既知の制約

- 番組表があるのは再生確認済みチャンネルの約 4 割(ガイド未整備のチャンネルは表示なし)
- データは日次更新のため、当日の編成変更(スポーツ延長等)には追従しない
- 取得日数は既定 2 日(それ以降の番組は「提供期間外」表示)
- グラバーの各サイトは HTML スクレイピングを含むため、サイト側の改修で
  一部サイトが一時的に取得不能になり得る(サイト単位の失敗は他サイトに影響しない)

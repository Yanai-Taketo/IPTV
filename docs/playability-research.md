# 視聴できないチャンネルを減らすための調査・検討

**日付**: 2026-08-04 / **ブランチ**: `claude/iptv-playability-research`

「HTTPのみ」「CORS未対応」で視聴できないチャンネルをなるべく減らしたい、という要望に対する
定量調査・事例調査・技術検討の結果と、その結論に基づいてこのブランチに実装した対策をまとめる。

## 1. 定量調査: 何が原因でどれだけ再生できないのか

iptv-org の全ストリーム(17,871件)から無作為抽出した **1,500 件を実際にプローブ**した
(GET + `Origin` ヘッダ送信・リダイレクト追跡あり。動的 CORS = Origin をエコーするサーバも検出)。

| 分類 | 割合 | 打てる手 |
|---|---:|---|
| ✅ ブラウザ再生可能(https・到達・CORS OK) | **56.8%** | — |
| ⚫ 応答なし(死亡・タイムアウト・4xx/5xx) | **30.5%** | **隠す/下位に下げる以外にない** |
| 🟡 生存だが HTTP のみ(混在コンテンツ) | 6.5% | プロキシのみ(https 昇格は 0.7pt しか効かない) |
| 🟠 生存だが CORS なし | 1.1% | プロキシ or Safari ネイティブ再生 |
| ❔ 非標準ポート https(計測環境の制約で不明) | 5.1% | — |

### 重要な発見

1. **「CORS 問題」は想定よりはるかに小さい(全体の約 1%)。**
   hls.js は `Origin` ヘッダを送るため、Origin をエコーする動的 CORS サーバ(検証では
   ACAO 無しに見えた 165 件中 133 件)が実際には再生できる。リダイレクト先(244件)も
   全件 CORS 対応だった。単純な `curl` 計測は CORS 非対応率を大幅に過大評価する。
2. **視聴不可の主因(30.5%)は「死んでいる配信」**であり、プロキシでもどうにもならない。
3. **プロキシで救える上限は 7.7%**(HTTP のみ 6.5% + CORS なし 1.1%)。
4. **http→https 昇格はほぼ効かない**(http 318 件中、https で応答したのは 11 件 = 3.5%)。
   IPTV サーバの大半は 8080 等の平文ポート運用で、TLS を話せない。

> 計測環境の注意: この環境の egress プロキシは 443 番以外の HTTPS を通せないため
> 5.1% は判定不能(実際の再生可能率はこれより数ポイント高い可能性がある)。
> ジオブロック(403)は計測地点依存で、日本からは再生できるものも含まれうる。

## 2. 事例調査: 他のプレイヤーはどうしているか

| プレイヤー | 方式 |
|---|---|
| **iptv-org 公式サイト** | ブラウザ再生を**そもそも行わない**(URL コピー → VLC へ)。品質管理はデータセット側(ffprobe による死活チェックで壊れたリンクを削除) |
| **tv.garden**(最も普及) | **サーバ側で再生可能性を事前チェックし、通ったものだけ表示**(プロキシなし・エラーなし・リストは小さくなる) |
| **IPTVnator** (PWA) | プレイリスト/EPG などメタデータのみ自前プロキシ、**映像はプロキシしない**。失敗時は「VLC で開いて」 |
| **IPTV-Restream** | ffmpeg 常駐のフル再送信プロキシ(**セルフホスト前提**のツールとして提供) |
| **Wizju 等** | Chrome 拡張版で CORS を回避(Web 版は諦める) |

→ 業界の共通解は **(a) 事前チェックで死んだ配信を見せない**(tv.garden 方式)と
**(b) 共有プロキシはホストせず、必要ならユーザー自身に持たせる**、の 2 点。

## 3. プロキシ方式の検討結果(なぜ「共有プロキシ」をやらないか)

- **法的**: リンク集(iptv-org の立場)と、バイトを中継する再送信は法的に別物。
  無許諾再送信は ABC v. Aereo(米)・ITV v. TVCatchup(EU)で敗訴が確立しており、
  「元が無料放送」は抗弁にならない。DMCA 通知の宛先が「リンク削除」から
  「あなたが再配信者」に変わる。
- **コスト**: HLS 3Mbps ≒ 1.35GB/時/視聴者。無料枠で最も現実的な Cloudflare Workers
  (10万リクエスト/日)でも **1日あたり約55視聴時間で枯渇** = 個人利用サイズ。
  Deno Deploy は 100GB/月(≒74視聴時間/月)で論外。
- **悪用**: 静的サイトには秘密を置けないため、共有プロキシは構造的にオープンプロキシになる
  (cors-anywhere が 2021 年に閉鎖的運用へ追い込まれた前例)。
- **ToS**: 2023 年改定以降、workers.dev での動画プロキシ自体は Cloudflare ToS 違反ではない
  (ただし独自ドメインの CDN 経由に載せると動画制限が復活)。

→ **結論: プロジェクトとしてプロキシはホストしない。**
ユーザーが**自分専用**のプロキシ(下記参考実装)を任意で設定できる口だけ用意する。

## 4. 採用した対策(このブランチで実装済み)

効果の大きい順:

1. **再生可能性インデックス**(最重要・対象 30.5%+)
   - `scripts/probe-streams.mjs` が全ストリームをプローブし `data/playability.json` を生成
     (1=再生可能見込み / 2=HTTPのみ / 3=CORSなし / 0=応答なし)
   - `.github/workflows/probe-playability.yml` が**毎日自動更新**(要デフォルトブランチへのマージ。
     手動実行は Actions → Probe stream playability → Run workflow)
   - アプリ側: ✓確認済バッジ/「応答なし」の淡色表示、**「再生確認済みのみ」フィルタ**、
     一覧を確認済み→未確認→応答なしの順に自動整列、チャンネル内でも確認済みソースを最優先で試行
   - インデックスが無い環境でも従来どおり動作(任意ファイル)
2. **Safari/iOS でネイティブ HLS を優先 + hls.js 失敗時のネイティブ再試行**(対象: CORS なし 1.1%)
   - ネイティブの media 読み込みは CORS 制約を受けないため、Safari では CORS 未対応配信も再生できる
   - video.js / JW Player など主要プレイヤーも Apple 環境ではネイティブ優先が標準
3. **混在コンテンツの https 昇格を 1 回だけ試行**(対象: 0.7%)
   - 失敗しても追加コストは 1 リクエストのみ(http のままでは送信前にブロックされるため損はない)
4. **任意プロキシ設定**(既定 OFF・対象: 最大 7.7%)
   - フッター「詳細設定」に プロキシ URL を保存すると、HLS(hls.js カスタムローダーで
     マニフェスト/セグメント/AES キー全て)と DASH(リクエストインターセプター)が
     プロキシ経由になる。**自分専用のプロキシのみ設定すること。**

## 5. 参考: 自分専用 Cloudflare Worker(任意)

個人利用の範囲であれば Workers 無料枠(10万req/日)に収まる。以下は最小構成の例
(自分のアカウントにデプロイし、URL をアプリの詳細設定に `https://xxx.workers.dev/?url=` として登録):

```js
export default {
  async fetch(req) {
    const url = new URL(req.url).searchParams.get('url');
    if (!url || !/^https?:\/\//.test(url)) return new Response('bad request', { status: 400 });
    // 任意: 自分のページからのアクセスに限定(ブラウザ以外には効かない簡易ガード)
    // if (req.headers.get('origin') !== 'https://<あなたのユーザー名>.github.io') return new Response('forbidden', { status: 403 });
    const upstream = await fetch(url, { headers: { 'User-Agent': 'Mozilla/5.0' } });
    const h = new Headers(upstream.headers);
    h.set('access-control-allow-origin', '*');
    return new Response(upstream.body, { status: upstream.status, headers: h });
  },
};
```

注意: プロキシを通した瞬間、帯域・アクセスログ・著作権上の責任は運用者本人に移る。
公開サイトの既定値として配布しないこと(本アプリは既定 OFF)。

## 6. 見送った案

| 案 | 見送り理由 |
|---|---|
| プロジェクトホストの共有プロキシ | §3 のとおり(法的・コスト・悪用) |
| ブラウザ拡張での CORS 解除 | 配布・審査コストが高く、Web ページの範疇を超える |
| mpegts.js 等による生 TS 対応 | 対象が 5 件/17,871 件でコストに見合わない |
| Chrome の自動昇格頼み | hls.js は fetch を使うため media 要素の自動昇格は適用されない |

## 6.5 初回フル実行の結果と計測バイアス

2026-08-04 の初回フルプローブ(GitHub Actions ランナー、17,968 URL):
再生可能 5,846 (32.5%) / 応答なし 10,016 (55.7%) / HTTPのみ 1,958 (10.9%) / CORSなし 148 (0.8%)。

サンプル調査(§1)より「応答なし」が大幅に多いのは、**GitHub ランナー(米国 Azure)の
IP レンジを IPTV サーバ側がブロック/地域制限しているバイアス**が主因とみられる。
つまり「応答なし」には**視聴地域からなら再生できる配信が相当数含まれる**。
このためアプリは「応答なし」を既定では隠さず、淡色表示+下位ソートに留めている
(完全に隠すのは「再生確認済みのみ」を明示的にオンにしたときだけ)。
将来の改善候補: 複数リージョンからのプローブ、失敗種別(タイムアウト vs 403)の記録。

## 7. 期待効果まとめ

- 「見えているのに再生できない」チャンネルの主因(応答なし 30.5%)は、
  インデックスにより**既定で下位に沈み、ワンクリックで完全に非表示**にできる
- 「再生確認済みのみ」表示時は、体感の再生成功率が **56.8% → ほぼ 100%** になる
  (確認時点との時差による揺らぎを除く)
- Safari ユーザーは CORS 未対応配信(1.1%)も追加で再生可能
- どうしても残る HTTP のみ配信(6.5%)は、任意プロキシ or 従来どおり
  「URL コピー / .m3u で VLC へ」で対応
